1. TÄTIGKEITEN HEUTE
--------------------

- Daten vom Code getrennt: Flask-Backend mit SQLite
  aufgebaut (Version 0.7):

  · data/trees.json als neue Datendatei. Die
    Genre-Bäume stehen nicht mehr im JavaScript.
  · seed.py liest die JSON-Datei und schreibt sie in
    die SQLite-Tabelle "nodes" (62 Zeilen). Der Baum
    entsteht über die Spalte parent_id.
  · app.py (Flask) liefert die Daten über den
    Endpunkt GET /api/trees als JSON.
  · Das Frontend lädt die Daten per fetch: zuerst
    über die API, sonst aus der JSON-Datei. So läuft
    die Live-Demo auf GitHub Pages ohne Server weiter.
  · Neue Datei .gitignore (Datenbank und __pycache__
    bleiben aus dem Repository heraus).

- Schreiben ermöglicht: POST /api/works legt neue
  Werke an — in der Datenbank UND in der JSON-Datei.
  Grund: Die Datenbank wird aus der Datei erzeugt.
  Würde nur die Datenbank geändert, wäre der Eintrag
  nach dem nächsten seed.py weg. Schlägt das Schreiben
  der Datei fehl, rollt der Server die Datenbank
  zurück (beide Stellen bleiben gleich).

- Formular "＋ Werk hinzufügen" im Browser. Es
  erscheint nur bei laufendem Backend; auf der
  Live-Demo steht stattdessen ein Hinweis, weil
  GitHub Pages kein Python ausführen kann.

- Eigene Titelbilder erzeugt (Version 0.8):

  · Recherche vorher: Die deutsche Wikipedia zeigt
    keine Buchcover (nicht-freie Dateien sind dort
    nicht erlaubt), die englische nur unter
    "fair use". Fremde Bilder wären für dieses
    Repository rechtlich nicht sauber.
  · Entscheidung: Bilder selbst erzeugen. Das
    Skript generate_covers.py schreibt für jedes der
    43 Werke eine SVG-Datei nach data/covers/ und
    trägt den Pfad ins Feld "cover" ein.
  · Bauplan: Kategorie oben, Titel in Serife in der
    Mitte, Autor in Monospace, Zweigmotiv unten, ★
    oben rechts. Nur die Farben aus :root.
  · Das Skript ist deterministisch: der Hash der
    Werk-ID wählt Verlauf und Lichtpunkt. Zweimal
    ausgeführt ergibt byte-identische Dateien
    (SHA-256 geprüft).
  · Fehler dabei gefunden und behoben: In der zweiten
    Zeile stand zuerst der Werktitel statt der
    Kategorie ("DUNE" statt "SCIENCE FICTION").
    Ursache war ein Schritt zu viel im rekursiven
    Durchlauf des Baums.
  · Wikipedia-Links: 40 von 43 Werken haben einen
    Artikel. Die Links stehen als Feld "wiki" in den
    Daten und werden nicht aus dem Titel berechnet.
    Grund: "1984" zeigt in der deutschen Wikipedia
    auf den Artikel über das Jahr, nicht über den
    Roman. Drei Werke haben keinen Artikel und
    bleiben ohne Link.

- Buchkarte als Poster umgebaut (Version 0.9):

  · Das Titelbild füllt jetzt die ganze Karte
    (Seitenverhältnis 2:3), darunter liegt eine
    dunkle Leiste mit Beschreibung und Knöpfen.
  · Titel und Autor stehen auf dem Bild und werden
    auf der Karte nicht wiederholt.
  · Ebenen mit nur Werken nutzen engere Spalten
    (grid-books, ca. 185 px) — die Kategorie wirkt

  · Sonderfälle abgefangen: Werk ohne Bild bekommt
    eine Ersatzfläche, hochgeladene Fotos (ohne
    eigene Schrift) bekommen Titel und Autor als
    Zeile auf dem Bild.
  · Fehler dabei gefunden und behoben: Der erste
    Entwurf zeigte zwei Sterne ("★★"), weil der
    Stern im Bild UND als Badge erschien. Das Badge
    gibt es jetzt nur bei Bildern ohne eigene Schrift.

- Alles im Browser geprüft, in beiden Betriebsarten

  Navigation, "Mehr anzeigen", Cross-Media-Sprung
  (No Longer Human Roman ↔ Manga), ★, Breadcrumb,

2. WAS ICH GELERNT HABE
-----------------------

- Wie eine dreistufige Datenkette funktioniert:
  JSON-Datei -> SQL-Tabelle -> API. Und warum man
  beim Schreiben an zwei Stellen denken muss, wenn
  eine Stelle die andere erzeugt.

- Was parent_id bedeutet: Ein verschachtelter Baum
  liegt als flache Tabelle, in der jede Zeile auf
  die übergeordnete Kategorie zeigt. Der Baum wird
  beim Auslesen rekursiv zusammengesetzt.

- Dass SVG-Dateien Text sind: Flächen, Linien und
  Schrift als Markup, etwa 3 KB pro Bild. Deshalb
  kann ein Skript sie erzeugen, und sie brauchen
  keine Fremdbilder.

- Warum Empfehlungen "fair use" nicht für eigene
  Webseiten gelten und was "nicht-freie Dateien" in
  der Wikipedia praktisch bedeutet.

- Warum man Wikipedia-Links nicht aus Titeln
  berechnen darf ("1984" das Jahr) und dass man
  Suchergebnisse prüfen muss, bevor man sie
  übernimmt (ein Suchtreffer lieferte ein Foto von
  Indira Gandhi).

- Dass auf diesem Rechner zwei Python-Installationen
  existieren ("python" hat Flask, "py" nicht) und
  wie man das mit python -m pip gezielt behandelt.

- Wie CSS Grid mit minmax unterschiedliche
  Spaltenbreiten für Kategorien und Poster erlaubt,
  gesteuert über eine Klasse am Container.
